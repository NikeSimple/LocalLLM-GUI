## 3. Интеграционное тестирование

Проверяется взаимодействие **реальных репозиториев** с **реальной SQLite** через Qt SQL. Тесты используют классы `DialogRepository`, `MessageRepository`, `PromptRepository` — то есть тот же код, что и в приложении, а не моки.

**Сценарии:**
1. Создание диалога → чтение → проверка полей (id, title, model_name, timestamps).
2. Добавление сообщений к диалогу → чтение → проверка порядка и содержимого.
3. Удаление диалога → проверка каскадного удаления сообщений.
4. Полный CRUD по шаблонам промптов.
5. Активация/деактивация шаблона (состояние чекбокса).

**Результат:** все сценарии проходят без ошибок. Каскадное удаление работает, `PRAGMA foreign_keys = ON` включён.

## 4. Тестирование безопасности

**Проверка защиты от SQL-инъекций.**

Приложение использует **параметризованные запросы** через `QSqlQuery::prepare()` и `bindValue()` — не конкатенацию строк. Это соответствует разделу 4.5.5 ТЗ.

**Тестовые сценарии:**
- Инъекция через title диалога: `'; DROP TABLE dialogs; --`
- Инъекция через содержимое сообщения: `'; DELETE FROM messages; --`

**Результаты:**
- Таблица `dialogs` не удалена после инъекции.
- Опасная строка сохранена как обычный текст, не выполнена как SQL.
- Сообщение с инъекцией сохранено, но другие сообщения не удалены.
- Количество записей соответствует ожидаемому.

**Вывод:** защита от SQL-инъекций работает корректно.

## 6. Производительность

**Измерения проводились вручную** на конфигурации:
- Windows 10/11, MSYS2 UCRT64.
- GPU: NVIDIA GeForce RTX 4060 Laptop (8 ГБ VRAM).
- Модель: `llama3.1:8b` (~5 ГБ).

| Параметр | Значение | Примечание |
|----------|----------|------------|
| Запуск приложения (прямой) | **1.3 сек** | Из папки `build/` |
| Запуск через ярлык | 5.2 сек | Задержка синхронизации OneDrive |
| Открытие диалога из списка | **< 100 мс** | Мгновенно |
| Холодный старт генерации | 18 сек | Загрузка модели в VRAM |
| Тёплый старт генерации | **4 сек** | Модель уже в VRAM |
| Потребление ОЗУ в интерфейсе | 21 МБ | Стабильно, растёт нагрузка на CPU |

**Пояснения:**
- **Холодный старт** (18 сек) — нормальное поведение Ollama: при первом запросе модель загружается с диска в VRAM. Это разовая задержка.
- **Тёплый старт** (4 сек) — реальная скорость отклика при повторных запросах. Модель остаётся в памяти в течение `keep_alive=5m`.
- **Запуск через ярлык** медленнее из-за OneDrive-синхронизации папки Desktop — это особенность конкретной конфигурации, а не приложения.

## 8. Автоматизация (CI/CD)

Настроен **GitHub Actions** — файл `.github/workflows/build.yml`.

**Что делает workflow при каждом push:**
1. Разворачивает Ubuntu-виртуалку.
2. Устанавливает Qt 6, SQLite, CMake, g++.
3. Конфигурирует проект через CMake.
4. Собирает `.exe` (в Linux-исполнении).
5. Запускает `ctest` — все 58 тестов.

**Результаты последних запусков:**

- Build and Test #3 (merge) — ✅ успех

Время одного прогона — 47–120 секунд.

## 9. Найденные и исправленные ошибки

За время разработки были найдены и исправлены следующие проблемы:

| Проблема | Причина | Решение |
|----------|---------|---------|
| Диалоги пропадали при пересборке | БД создавалась в `build/`, удалялась `rm -rf build` | Путь изменён на `../localllm.db` — БД в корне проекта |
| Кракозябры в консоли | Windows-консоль в CP866, код в UTF-8 | `SetConsoleOutputCP(CP_UTF8)` в `main()` |
| Шаблоны не объединялись | Применялся только один шаблон | Добавлены чекбоксы, активные шаблоны объединяются |
| Приложение не собиралось | Пустые `.cpp` файлы в `CMakeLists.txt` | Удалены мёртвые файлы (logger, context_builder и др.) |
| Push workflow отклонён | Токен без scope `workflow` | Загружено через веб-интерфейс GitHub |
| Конфликт при pull | `build.yml` создан и локально, и через веб | Разрешён через merge |
